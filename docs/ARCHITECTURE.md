# Family 100 architecture

## Deployment decision
Use Cloudflare Workers Static Assets plus one SQLite-backed Durable Object. This runs in the user's own Cloudflare account. Workers hosting supports asset bindings and API routing. SQLite Durable Objects are supported on Workers Free. No always-running VM, external database, paid-only Durable Object storage, or Google Sheets connector is needed.

## Components
- public/: adapted host page, six team entry pages, shared client code and styles. Reference artifact/ is retained.
- src/worker.js: request routing, same-origin validation, session signing/verification, asset binding, Durable Object routing.
- src/game-room.js: persisted game state, serialized commands, connection role projections, live broadcasting.
- src/game-engine.js: platform-independent normalization, matching, ownership, scoring, and validation for meaningful tests.
- tests/: engine, authorization/projection, persistence, and API integration checks.
- wrangler.jsonc: assets directory, API Worker routing, Durable Object binding and new_sqlite_classes migration. Package scripts cover dev/test/deploy/dry-run.

## Identity and access
HOST_PASSWORD is a Worker secret, never a public asset or committed default. Host login creates an expiring signed HttpOnly Secure SameSite session; local development may relax Secure only for loopback HTTP. Add bounded login attempts. Each team receives an unguessable invitation generated by the server. Exchange an invitation for a scoped session; keep codes out of logs and analytics. Role is derived from verified session, not a client-supplied team number. A host can obtain/rotate invitation links. Use relative/same-origin links. Treat host sessions, invitation credentials and backups as private. Same-origin checks protect mutation requests and WebSocket upgrades. Bound payloads, names, answers, questions, and per-round submissions.

## Data model
- Game: schema version, revision, active question ID, six teams, settings, invitation hashes/records.
- Question: stable ID, text, ordered answers (stable answer ID, text, points, aliases).
- Round: question ID, generation, locked state, revealed answer IDs, ownership snapshot, optional multiplier, adjustment state.
- Submission: server-issued increasing sequence, stable question ID, round generation, team identity, text, normalized text, server timestamp, matched answer ID.
- Session: role/team, expiry, signature; no host password in persistent game records.

Server timestamps and sequences decide precedence. Client timestamps are never authoritative. Use atomic synchronous SQLite transactions or equivalent Durable Object serialization for every check-and-mutate path. Do not await external operations between duplicate/lock validation and the accepted write. Publish snapshots only after committed writes.

## Rules
1. Only the active unlocked question/generation accepts submissions. Team cannot select future questions or bypass locking by changing its request.
2. Match normalized answers and declared synonyms consistently on the server. Deterministic tie handling. First accepted owner of each board answer gets its points; same-team repeats and other-team duplicate claims are rejected with clear feedback. Unmatched guesses may be stored as submissions without points.
3. Lock and submit are ordered by the server. Revealing the first answer auto-locks in the same mutation. A round's accepted answers/owners remain stable after lock.
4. Scores derive from revealed correct answers plus explicit host adjustments. Hiding an answer reverses its awarded score consistently with the reference; re-reveal must not double count.
5. Question reordering uses stable IDs and does not reassign past submissions. Prevent scoring edits to completed/started rounds unless their gameplay is explicitly reset; explain this in the editor.
6. Reset advances generation and clears gameplay consistently. Stale requests cannot contaminate the next game. Retain questions/team names unless the host explicitly restores sample content.
7. Host changes and gameplay persist centrally; localStorage holds only non-sensitive preferences or migration data.

## API contract (names may be refined coherently)
- POST /api/host/login and POST /api/logout
- POST /api/team/join (invitation exchange)
- GET /api/state (role-filtered snapshot)
- GET /api/live (authenticated WebSocket upgrade)
- POST /api/host/command (question edits, active question, lock, reveal/hide, score adjustment, reset, invitation rotation)
- POST /api/team/submit (text, expected question ID/generation, optional idempotency ID)
- Host-only export/import for a versioned backup, with validated contents and explicit replacement confirmation.

Return structured errors with stable codes and readable Indonesian messages. Include revision, question ID, and generation in snapshots. Host projection includes editor data and all submissions; team projection includes only its own submissions, team identity, round status and any intentionally public revealed data. Do not ship answer banks to team JavaScript or bootstrap.

## Live synchronization
Prefer hibernating WebSockets so idle connections do not require polling. Store verified connection roles in socket attachments, rebuild from persisted state after hibernation, and send full authoritative snapshots on connect/reconnect. Reject expired sessions on messages and before role-sensitive broadcasts. Commands may use HTTP while sockets only deliver snapshots. A bounded reconnect with backoff must recover without duplicate sends. Free quotas still apply; no zero-cost or unlimited-usage guarantee. If the runtime is unavailable locally, document the exact validation limitation rather than inventing a successful check.

## Operational boundaries
One game per deployment is sufficient for the supplied mockup. Multiple rooms, accounts, tournaments, QR artwork, and unrelated features are out of scope. The host is trusted to operate the game; teams must not gain host access. A workers.dev hostname is enough for initial deployment; custom domain setup is optional. Deploying static HTML alone to Pages would not supply the shared database; the Worker package is the complete deployment target.

## Visual direction
The supplied reference is the design authority: Indonesian game-show studio, navy/royal blue board, gold answers and controls, six distinct team identifiers, condensed headings, projector-friendly composition. Reuse existing assets and typography rather than inventing a brand. Preserve mockup functionality while making team pages usable on phones. Set energy/rhythm/motion from this reference when the pending skill-mode question is answered.

## Total storage and payload bounds

Persisted game JSON is limited to 1,800,000 UTF-8 bytes, checked before the SQLite transaction and before replacing in-memory state. Rejection leaves the previous committed game intact. Individual maxima do not imply their Cartesian maximum fits. Standard JSON routes default to 200,000 bytes; host question commands permit 800,000 bytes; authenticated backup restoration permits 2,000,000 bytes. Compact backup downloads and the browser file check use the matching restore limit.
